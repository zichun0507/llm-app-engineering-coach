# RAG 检索质量与评测体系

> 什么时候读这个文件：用户在搭 RAG、抱怨"答得不准/检索不到"、要设计评测集，或者要判断该改检索还是改模型。

---

## 1. 一句话判断

**RAG 系统 80% 的效果问题出在检索，不在模型。**

检索错了，后面再好的模型也只是在认真地把错误答案说得更漂亮。

**最省时间的判断法则**：如果 `recall@10` 不到 80%，**别动 Prompt，先去修检索**。

---

## 2. 六道工序

```
原始文档
  │ ① 解析清洗（PDF 表格、页眉页脚、乱码）
  │ ② 分块 Chunking
  │ ③ 向量化 + 建索引
  ▼
用户提问 → ④ 查询改写 → ⑤ 混合召回 + 重排 → ⑥ 上下文组装 → 模型
```

### ① 解析清洗

最脏、最容易被跳过、收益最大。PDF 表格、双栏排版、页眉页脚没处理干净，检索出来全是噪音。**这一步做到位，提升经常超过换 embedding 模型。**

### ② 分块

- **结构优先**：按标题层级、条款、函数边界切；别按固定字数硬切（切碎一个完整条件句，神仙也救不回）
- **尺寸**：300–800 token，overlap 10%–15%
- **父子块（small-to-big）**：小 chunk 做检索保证精准，命中后返回父级大块保证上下文完整。性价比极高
- **元数据必带**：标题路径、来源、时间、版本、权限标签——后面做过滤和引用全靠它

### ③ 向量模型

中文可选 BGE-M3、GTE、Qwen-Embedding 等。维度高不等于好，要看**你的领域**。垂直领域用几千条自有数据微调 embedding，效果提升常常比换大模型更明显。

### ④ 查询改写

用户的提问通常很烂（"这个怎么弄？"）：

- **多查询扩展**：生成 3 个不同角度的 query，并集召回
- **HyDE**：先生成假想答案，拿它去检索（答案和文档更像）
- **问题拆解**：多跳问题拆成子问题分别检索
- **指代消解**：结合历史把"它""那个"还原成实体

### ⑤ 混合召回 + 重排（**优先级最高**）

```python
def retrieve(query: str, tenant_id: str, k: int = 50, top_n: int = 6):
    # 稠密检索：语义相近
    dense = vector_store.search(embed(query), k=k, filters={"tenant": tenant_id})

    # 稀疏检索：关键词/编号/专有名词，向量模型对这类天生弱
    sparse = bm25.search(query, k=k)

    # 倒数排名融合（RRF），两种召回的天然互补
    fused = rrf_fuse([dense, sparse], k=60)[:k]

    # 交叉编码器重排：query 和 chunk 一起进模型打分，精度远高于向量相似度
    reranked = reranker.rerank(query, fused, top_n=top_n)

    # 头尾放最相关的，规避 lost in the middle
    return interleave_ends(reranked)
```

**调优优先级（按 ROI 从高到低）**：

```
重排 > 混合检索 > 分块优化 > 查询改写 > 换 embedding > 换大模型
```

很多团队一上来换更大的模型，发现没用——**因为检索压根没把对的资料捞出来**。

### ⑥ 上下文组装

- Top 5–8 就够，多了全是噪音还稀释注意力
- 每块标来源编号，方便引用与事后校验
- 加时效提示（"上述资料截止于 2026-03"），减少时效幻觉

## 3. 评测：三层指标

| 层级 | 评什么 | 指标 | 怎么测 |
|---|---|---|---|
| 检索层 | 该找的找到了吗 | Recall@k、MRR、nDCG | 人工标黄金片段，纯代码算 |
| 生成层 | 答得忠实吗 | Faithfulness、Answer Relevancy、Context Precision/Recall | LLM 裁判（RAGAS 类） |
| 业务层 | 任务完成了吗 | 任务成功率、首答解决率、转人工率、满意度 | 人工抽检 + 埋点 + A/B |

**只测第二层是最常见的自欺欺人**——生成层分数很好，但检索没召回，等于模型在很认真地瞎编。

---

## 4. 黄金测试集怎么建

**这是核心资产，比代码重要。**

- **规模**：100–300 条起步，追求**代表性**不追求大
- **来源**：从线上真实日志抽，不要自己编
- **分层**（每类都要有）：
  - 单跳事实题
  - 多跳组合题
  - 否定/排他题（"除了 A 还有哪些"）
  - **无答案题**（必须拒答，专测幻觉）
  - 时效性问题
  - 口语化 / 错别字 / 超短问题
  - 长尾实体
- **每条要有**：问题 + 标准答案要点 + 黄金片段 ID + 可接受变体

**"无答案题"千万别省**——这是唯一能定量衡量幻觉率的入口。

---

## 5. LLM-as-Judge 的四个坑

1. **位置偏见**：A/B 对比偏爱第一个 → **交换顺序各评一次**，取一致结果
2. **长度偏见**：偏爱长答案 → rubric 里明确写"简洁不扣分"
3. **自我偏好**：同家模型打分偏高 → 裁判与被告用不同厂商
4. **打分校准**：1–10 分方差巨大没意义 → 改成**二值判断**（"答案是否完全被资料支持：是/否"），并拿 50 条人工标注校准一致率

**一致率低于 80% 的裁判，不要信它。**

## 6. Eval as Code

```
每次改动（Prompt / 检索参数 / 模型版本 / chunk 策略）
        ↓
自动跑黄金集 → 对比报告（分数变化 + 失败样例 diff）
        ↓
回归门禁：核心指标掉超过 2% → CI 拦住，不许合
```

上线记录三元组：`prompt_version + model + retrieval_config`。出问题才能精确定位回滚。

**Prompt 也是代码，必须版本化、必须回归。**

## 7. 线上监控指标

| 类别 | 指标 |
|---|---|
| 性能 | p95 延迟、首字延迟、QPS |
| 成本 | 单次成本、token 用量、缓存命中率 |
| 质量 | 拒答率、转人工率、幻觉抽检率（每天抽 50 条让裁判过） |
| 体验 | 点赞率、点踩率、编辑距离（对建议类场景） |

## 8. 常见误判

| 现象 | 真实原因 | 该做什么 |
|---|---|---|
| 答非所问 | 检索召回错 | 先测 recall@10 |
| 编造细节 | 无答案兜底缺失 | 加拒答规则 + 无答案样本 |
| 引用编号对不上 | 上下文组装时没标来源 | 每块带 id，强制引用 |
| 换个说法就查不到 | 纯向量检索，无关键词 | 加 BM25 混合 |
| 中文数字/编号查不到 | 分词与归一化问题 | 预处理统一格式 |
| 长文档答不全 | 分块切断了上下文 | 父子块 + 适当 overlap |
| 越用越慢 | 上下文无限增长 | 滚动摘要 + 只保留最近 N 轮 |
