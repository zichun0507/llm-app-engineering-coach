# Agent Skill 的编写

> 什么时候读这个文件：用户问 skill 是什么、怎么写 skill、description 怎么调、skill 和 prompt/tool 有什么区别。

---

## 1. 先分清四样东西

| 东西 | 是什么 | 生命周期 | 类比 |
|---|---|---|---|
| Prompt | 一次性指令 | 本次对话 | 今天口头交代的事 |
| **Skill** | 可复用的**流程知识包** | 跨会话，按需加载 | SOP 手册 + 工具箱 |
| Tool / MCP | 能**执行动作**的能力 | 常驻注册 | 手和钥匙 |
| Subagent | 独立上下文的执行者 | 一次任务 | 派出去的同事 |

**一句话定位：Tool 给"能做什么"，Skill 给"该怎么做"。**

Skill 不增加模型能力，它增加**判断力和流程**——什么时候用什么工具、按什么顺序、产出什么格式、边界在哪。

---

## 2. 本质：书脊 → 正文 → 附录

**Skill = 一个文件夹 + 一份说明书 + 可选脚本。模型平时看不见它，只在需要时翻开那一页。**

三级加载（渐进式披露）：

| 层级 | 内容 | 何时进上下文 | 预算 |
|---|---|---|---|
| **L1 元数据** | `name` + `description` | **永远在** | 约 100 词 |
| **L2 正文** | `SKILL.md` | 触发后加载 | **< 500 行** |
| **L3 资源** | `scripts/` `references/` `assets/` | 需要时 | 无上限 |

推论：

- **description 决定"要不要看"**
- **正文决定"怎么做"**
- **references 决定"细节在哪"**

**精妙之处**：script 可以被**执行而不被读取**。一个 500 行脚本，模型不需要看懂，只要知道"跑它"——零上下文成本。

---

## 3. 目录结构

```
skill-name/
├── SKILL.md            ← 必需
├── scripts/            ← 可选：确定性脚本
├── references/         ← 可选：按需读取的细节
├── assets/             ← 可选：模板、图标、字体
└── evals/              ← 可选但强烈建议：测试用例
```

```markdown
---
name: changelog-writer
description: 从 git 提交历史生成面向用户的 CHANGELOG。当用户提到"更新日志""release notes""发版说明""changelog"，或准备打 tag、发布新版本时使用。
---

# 目标
## 工作流
## 输出格式
## 边界
```

**frontmatter 两条硬规则**：

1. `name` 必须**小写 + 连字符**，且**与文件夹同名**。`changelog-writer` ✅，`ChangelogWriter` ❌
2. `description` 是**唯一触发机制**。写不好它，整个 skill 就是死代码

---

## 4. description 怎么写（最重要）

模型是**先看 description 决定要不要翻这本书**。它必须同时回答：**做什么 + 什么时候用**。

| ❌ | ✅ |
|---|---|
| "帮助处理文档" | "从 PDF 发票中提取金额、税号、开票日期。当用户提到发票、报销、财务凭证、PDF 账单，或想把 PDF 表格转成 Excel 时使用，即使用户没明确说'提取'。" |
| "写更新日志" | "从 git 提交历史生成面向用户的 CHANGELOG。当用户提到'更新日志''release notes''发版说明'，或准备打 tag、发布新版本时使用；即使用户只说'整理一下这次改了什么'也应触发。" |

三个技巧：

1. **写用户的原话**，不写工程术语。"整理一下这次改了什么"覆盖率远高于 "generate changelog"
2. **稍微贪心**。模型天然倾向**不触发**（undertrigger），描述要略微主动，把近义场景都列上
3. **该说"什么时候不用"**。两个 skill 重叠时，明确边界能大幅降低误触发

---

## 5. 优秀 skill 的六个标准

### ① 触发精准

见上。判断方法：拿 10 条真实用户会说的话，看它能不能都触发。

### ② 单一职责

**判断标准：能用一句话说清"它什么时候用"吗？** 说不清就是太大了。

```
❌ data-toolkit（读 Excel + 画图 + 建库 + 写报告）
✅ excel-reader / chart-builder / sql-writer
```

为什么：skill 是按需加载的。五件事塞一个包，用户只要画图，也得把 Excel 解析规则读进来——白烧 token 还稀释注意力。

**太大不要拆成多个 skill，而是在内部再分一层**：

```
cloud-deploy/
├── SKILL.md          ← 只做"选哪个云"的分流
└── references/{aws,gcp,azure}.md
```

### ③ 讲"为什么"，不堆"必须"

```markdown
❌ ALWAYS use snake_case. NEVER use camelCase.
✅ 字段名用 snake_case，因为下游 SQL 表也是 snake_case，
   不一致就要每次写映射层，容易错。
```

今天的模型很聪明：**给理由能泛化到没写到的场景，只给规则一出边界就懵**。

**信号**：当你开始写全大写 ALWAYS/NEVER 时，说明你还没想清楚为什么。

### ④ 渐进式披露

- 正文 < 500 行：经验值
- 参考文档 > 300 行：加目录，方便定向跳读
- 正文快超了：再加一层，明确告诉模型"下一步去哪读"

**判断：正文放"每次都要用的"，references 放"偶尔才需要的"。**

### ⑤ 确定性下沉到脚本

| 写脚本 | 写正文 |
|---|---|
| 格式转换（docx→pdf） | 判断"这份文档算不算合同" |
| 数据校验、去重 | 决定"用哪种抽取策略" |
| 固定模板渲染 | 措辞怎么调更自然 |
| 文件批处理 | 异常了怎么补救 |

**判断标准：同一件事做十次结果都一样 → 脚本；每次都要看情况 → 文字。**

**实战信号**：如果跑三个测试用例，模型每次都自己现写一个 `build_chart.py`，那这个脚本就该被打包进 `scripts/`。

### ⑥ 可评测

**"优秀"和"能跑"的分水岭。**

三个真实用户会说的话：

```
1. "帮我把这次发版的东西整理一下"     ← 正常触发
2. "README 里加一段更新说明"          ← 近似场景，该不该触发？
3. "把这周的 commit 按人统计一下"     ← 不该触发（不是 changelog）
```

跑两遍：**有 skill vs 没 skill**，对比三件事：

| 指标 | 看什么 |
|---|---|
| 质量 | 是否真按格式来、分类对不对 |
| token | skill 加载本身花了多少 |
| 时间 | 有没有因为多读文档反而变慢 |

**没有这个对比，你永远不知道 skill 是在帮忙还是在添乱。**

## 6. 完整示例

```markdown
---
name: changelog-writer
description: 从 git 提交历史生成面向用户的 CHANGELOG。当用户提到"更新日志""release notes""发版说明""changelog"，或准备打 tag、发布新版本时使用；即使用户只说"整理一下这次改了什么"也应触发。
---

# 目标
把原始 commit 转成用户可以读懂的变更说明，按 Keep a Changelog 分类。

# 工作流
1. 确定版本范围：`git log <上一个tag>..HEAD --oneline`。
   没有 tag 时取最近 50 条 commit，并明确告知范围。
2. 读 references/categories.md，判断每条属于 Added / Changed / Fixed / Removed。
3. 过滤 chore、ci、style、test——除非影响用户能感知的行为。
4. 按"用户能否据此决定要不要升级"重写措辞，不要照抄 commit message。
5. 按下方模板输出。

# 输出格式
始终使用以下结构，不要增删章节：

## [版本号] - YYYY-MM-DD
### Added
### Changed
### Fixed

# 措辞规则（为什么）
commit message 是写给开发者的（"fix nil check in parser"），
changelog 是写给用户的（"修复部分 PDF 文件解析失败"）。
判断标准只有一条：用户能不能据此决定要不要升级。

# 边界
- 版本号只建议，不自行推断语义化版本，需用户确认。
- 不在 git 仓库内时，请用户提供 commit 列表；不要编造提交内容。
```

要素齐全：触发词 → 工作流 → 固定模板 → 关键规则给"为什么" → 边界清晰 → 细节下沉。

## 7. 七个失败模式

| # | 失败模式 | 症状 | 修法 |
|---|---|---|---|
| 1 | description 太抽象 | 该触发不触发（最常见） | 加用户原话、近义场景、"即使没明说" |
| 2 | 正文写成散文 | 读完不知道从哪下手 | 编号工作流 + 固定模板 |
| 3 | 什么都往里塞 | 几千行大杂烩，token 爆炸 | 拆 reference，正文只留主路径 |
| 4 | 通篇 MUST/NEVER | 边界外就懵 | 每条规则补"为什么" |
| 5 | 把用户具体数据写死 | 换个文件就废 | 只写**模式**，不写**实例** |
| 6 | 没有测试 | 改完不知道好坏 | 3 个真实 prompt + 有无对比 |
| 7 | 违反"最小惊讶" | 说明书里藏了用户不知道的动作 | 用户看描述就能预判它做什么 |

第 7 条是底线：**如果用户读了 description 猜不到它会做什么，它就不该存在。**

---

## 8. 迭代闭环

```
写草稿（description + 正文）
      ↓
造 2–3 个真实测试 prompt
      ↓
跑「有 skill vs 无 skill」对比
      ↓
人看一眼输出 → 挑毛病
      ↓
改 skill（重点：删掉没用的部分）
      ↓
回到第二步，直到稳定
```

两个容易忽略的点：

1. **先删再加**。最容易犯的错是"再加一条规则"。**删掉一条重跑，分数不掉就永久删。** 价值密度是靠删出来的。
2. **看过程不只看结果**。如果模型花 8 个步骤做无用功，那不是输出格式问题，是正文里某句在误导它。

---

## 9. 收尾一句话

> **Skill 的本质，是把一个人的经验，变成所有人的默认行为。**
> 它不需要模型更聪明，只需要它在正确的时刻，看到正确的那一页。
