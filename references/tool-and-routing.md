# 工具设计与多 Agent 路由

> 什么时候读这个文件：用户要写工具描述、做 function calling / MCP 工具、Agent 工具太多不知道怎么办、或者要设计多 Agent 路由架构。

---

## 第一部分：工具描述

### 1. 心智模型

**工具描述不是 API 文档，是"选择依据"。**

模型面前摊开的是一张平的菜单，没有你的源码、没有业务背景。它只能靠这段文字判断三件事：

| 决策点 | 要回答的问题 | 靠什么 |
|---|---|---|
| 要不要调 | 需要工具吗？还是直接答？ | description 的"使用场景" |
| 调哪个 | 5 个相似工具选哪个？ | description 的"差异"和"不要用于" |
| 参数填什么 | 每个字段什么值、什么格式？ | parameters 的每个 field description |

对应三种失败：该调不调（场景没写清）、选错工具（差异没写清，**最高频**）、参数填错（约束没写清，**第二高频**）。

### 2. Name 命名

| ❌ | ✅ | 问题 |
|---|---|---|
| getData | get_order_detail | 太泛 |
| process | refund_order | 动词模糊 |
| order | create_order | 名词当工具名 |
| userTool2 | update_user_address | 编号命名必选错 |

规则：**动词 + 名词**；动词要有区分度（`search` 查列表 vs `get` 取单个）；snake_case；不要用同义词混着来（fetch/get/retrieve/query 混用会被当成四件不同的事）。

**名字里应包含 60% 的区分信息**，剩下 40% 交给 description。

### 3. Description 七行模板

```
【做什么】一句话，动词开头，说清产出
【何时用】触发条件，用用户的自然语言写
【何时不用】明确指向替代工具 ← 防选错
【返回什么】结构 + 体量 + 截断规则
【副作用】读/写/扣费/发消息，是否需要确认
【失败怎么办】错误语义 + 恢复动作
【边界】权限、频率、数据范围
```

### 4. 完整示例

```json
{
  "name": "search_orders",
  "description": "按手机号或关键词检索订单列表，只读操作，不会修改任何数据。\n\n使用场景：用户想查订单但没给出具体订单号时使用，例如「我上周买的东西到哪了」「查下我的订单」。\n\n不要用于：已知订单号要查详情 → 用 get_order_detail；要取消或退款 → 用 cancel_order；要查物流轨迹 → 用 track_shipping。\n\n返回：最多 20 条订单摘要（订单号、商品名、金额、状态、下单时间）。超过 20 条只返回前 20 条，并在 total 字段给出总数，此时应提示用户补充条件缩小范围。\n\n前置条件：phone 与 keyword 至少提供一个，两者都为空会返回 INVALID_ARGUMENT。\n\n失败处理：若返回 EMPTY_RESULT，说明该条件下无订单，应如实告知用户，不要猜测订单号。",
  "parameters": {
    "type": "object",
    "properties": {
      "phone": {
        "type": "string",
        "description": "用户手机号，11 位中国大陆号码，纯数字不含空格和横线。例如 \"13800138000\"。仅在用户提供手机号时填写。"
      },
      "keyword": {
        "type": "string",
        "description": "订单关键词，通常是商品名片段，例如 \"蓝牙耳机\"。支持模糊匹配，2-20 个字符。"
      },
      "status": {
        "type": "string",
        "enum": ["pending", "paid", "shipped", "completed", "cancelled"],
        "description": "按订单状态过滤，可选。不填返回全部。用户说「没发货的」对应 paid；「运输中」对应 shipped。"
      },
      "limit": {
        "type": "integer", "minimum": 1, "maximum": 20, "default": 10,
        "description": "返回条数上限，默认 10，最大 20。"
      }
    },
    "required": ["phone"]
  }
}
```

### 5. 五个参数坑

| 坑 | ❌ | ✅ |
|---|---|---|
| 类型万能化 | `"type":"string"` 的 status | **能枚举就枚举**，消掉一整类幻觉 |
| 格式不写清 | `"date":"日期"` | `"ISO 8601，YYYY-MM-DD，如 2026-03-15；相对时间需先换算"` |
| 单位不明 | `"amount":"金额"` | `"单位分，整数，100 表示 1.00 元"` |
| 必填/可选不清 | 只靠 required 数组 | description 里也写"不填会怎样" |
| 字段联动没写 | A、B 必须同时提供 | 在 description 里写成人话 |

日期、金额、手机号、地址、枚举是格式错误五大重灾区，**必须给示例值**。

### 6. 返回值与错误语义

必须写三件事：

1. **错误码枚举**——模型要区分"没找到"和"参数错了"，处理方式完全不同
2. **恢复动作**——"返回 CITY_NOT_FOUND 时提示用户检查，不要自行替换成相似城市"
3. **体量上限**——一次调用爆上下文，整轮报废

反面案例：某工具返回全文，描述只写"返回文档内容"，模型一次拿回 5 万字，后续推理全糊。加一句"单次最多 2000 字，超长截断，完整内容用 offset 分页"后解决。

### 7. 工具集设计四铁律

**铁律 1：工具数量是第一杀手。**

| 工具数 | 选择准确率（经验值） | 建议 |
|---|---|---|
| 1–5 | 很高 | 随便写都能用 |
| 6–15 | 良好 | 描述必须写清区分 |
| 16–30 | 明显下降 | 分组或动态筛选 |
| >30 | 开始乱选 | 必须重构 |

**铁律 2：按"用户意图"建工具，不按"后端接口"建。**

4 个只读查询接口 → 合并成 1 个 `get_customer_profile`。模型关心用户想干什么，不关心你有几张表。
但**不要为了减数量把语义不同的写操作合成一个**——参数变复杂反而更难用。

**铁律 3：读写分离。** 写操作必须在描述里标危险并要求确认，程序侧还要兜一层。

**铁律 4：命名空间防撞。** `search_docs` / `search_orders`，别都叫 `search`。

## 第二部分：多 Agent 工具路由

### 8. 心智模型：医院分诊台

一个医生什么病都看，队伍排到门外，而且每种病只懂一点。改成先过分诊台，分到专科——医生工具少、判断准、还快。**但分诊台自己会分错**，分错一次要重新排队。

对应关系：分诊台 = Router，科室 = 工具域/子 Agent，分错 = 误路由，转科 = Handoff，病历本 = 共享状态。

**核心命题：用"结构"换"准确率"。**

### 9. 先分清三种"多 Agent"

很多人嘴上说多 Agent，其实只需要第一种。成本差一个数量级。

| 形态 | 做法 | 成本 |
|---|---|---|
| **A. 动态工具集** | 一个模型，按域切换工具子集 | 最轻 |
| **B. 多角色 Agent** | 不同 system prompt + 工具 + 独立上下文 | 中 |
| **C. 独立服务** | 可并行、可异构模型 | 最重 |

**80% 的场景到 A 就够了。**

### 10. 五种路由范式

| 范式 | 适用工具量 | 路由准确率 | 延迟 | 成本 | 可控性 |
|---|---|---|---|---|---|
| ① 全量暴露 | ≤10 | 高 | 最低 | 最低 | 高 |
| ② 动态工具检索 | 11–30 | 中高 | 低 | 低 | 中 |
| ③ **域路由（动态工具集）** | 21–50 | **高** | 中 | 中 | **高** |
| ④ Supervisor + 子 Agent | 51–150 | 高 | 中高 | 高 | 中 |
| ⑤ 代码模式 / 工具网关 | 任意 | 取决于代码 | 高 | 中 | 极高 |
| ⑥ 状态机路由 | 任意 | **最高** | 低 | 低 | **最高** |

**③ 是主力方案**：路由的产物不是另一个 Agent，而是一个**工具子集**。

```python
DOMAINS = {
    "order":     {"desc": "订单查询、详情、取消", "tools": [search_orders, get_order_detail, cancel_order]},
    "aftersale": {"desc": "退款、退货、换货、售后进度", "tools": [create_refund, check_refund_status, create_return]},
    "logistics": {"desc": "物流轨迹、丢件、补发", "tools": [track_shipping, resend_package]},
    "account":   {"desc": "个人信息、地址、手机号", "tools": [get_profile, update_address]},
    "knowledge": {"desc": "政策咨询、常见问题", "tools": [search_faq, search_policy]},
}
```

### 11. 选型决策树

```
工具 ≤10？
 ├ 是 → ① 全量暴露，别折腾
 └ 否 → 描述清晰、语义可分？
         ├ 否 → 先修描述，别急着架构
         └ 是 → ≤30？
                  ├ 是 → ② + ③
                  └ 否 → 有明确业务域？
                           ├ 是 → ④ Supervisor
                           └ 否 → ⑤ 代码模式 / ⑥ 状态机
```

一句话判断：**拆的理由是"分不清"选③，是"任务太长要分工"选④，是"工具太杂"选⑤。**

### 12. 三层混合路由（推荐实现）

```python
def route(query, history, max_hops=5):
    """返回 domain key，或 'clarify' / 'fallback'"""

    # 第 1 层：规则快通道 —— 高频固定说法，0 延迟 0 成本
    hit = rule_match(query)          # "退款"→aftersale，"单号"→logistics
    if hit:
        return hit

    # 第 2 层：向量召回 —— 拿到候选，分差大就直接定
    cands = embed_route(query, top_k=3)
    if cands[0][0] - cands[1][0] > 0.15:
        return cands[0][1]

    # 第 3 层：LLM 终审 —— 只在模糊时调用
    return llm_router(query, candidates=cands, history=history)
```

| 层 | 覆盖 | 延迟 | 成本 |
|---|---|---|---|
| 规则 | 头部高频 | ~0ms | 0 |
| 向量 | 大多数正常表达 | ~10ms | 极低 |
| LLM | 模糊、多域、口语 | ~500ms | 低 |

LLM 只在"分差小"时才调，可把路由成本砍掉约 70%。

### 13. 路由 Prompt 要点

```markdown
# 任务
判断用户问题属于哪个业务域。只输出 JSON，不要解释。

# 域定义
- order: 查订单、看详情、取消订单
- aftersale: 退款、退货、换货、售后进度
...

# 判定规则
1. 只选一个域；涉及多个时选「需要先执行动作」的那个
2. 无法判断 → {"domain":"clarify","reason":"缺少关键信息"}
3. 不得输出域定义之外的值

# 输出
{"domain":"<key>","confidence":"high|medium|low","reason":"<20字内>"}
```

三条必做：**闭集输出**、**必须给 clarify 出口**、**必须带 reason**（线上排查误路由全靠它）。

### 14. 十个坑

| # | 坑 | 症状 | 解法 |
|---|---|---|---|
| 1 | 只路由一次，不回头 | 分错到底 | 允许子 Agent 返回 NEED_REROUTE，重路由 ≤2 次 |
| 2 | 子 Agent 回全量上下文 | 主对话 token 暴涨 | 强制摘要 ≤200 字 + 结构化字段 |
| 3 | A→B→A 死循环 | 延迟爆炸 | 跳数上限 + 不回访已访问域 |
| 4 | 路由层没评测 | 改了半年不知道好坏 | 单独建路由黄金集，200 条起 |
| 5 | 跨域任务失败 | "退货顺便看物流"只办了退货 | fan-out 或串行编排 |
| 6 | 域定义重叠 | "改地址"算哪个域 | 域定义互斥，重叠写优先级 |
| 7 | 命名不隔离 | 两个域都有 `search` | 强制前缀 |
| 8 | 路由即权限没做 | FAQ 链路能调退款 | 代码层按域白名单注入工具 |
| 9 | 每跳有日志但串不起来 | 定位不到哪一跳出错 | 统一 trace_id + 每跳 domain/hop/耗时 |
| 10 | 没跑基线就上架构 | 拆完还不如单 Agent | **先量再拆** |

### 15. 评测

| 指标 | 定义 | 经验目标 |
|---|---|---|
| 路由准确率 | 首次路由正确比例 | >92% |
| 端到端成功率 | 任务最终完成 | >85% |
| 平均跳数 | 一次会话经过几个域 | <1.5 |
| 误路由恢复率 | 分错后自愈 | >60% |
| P95 延迟 | 含所有跳 | 按业务定 |

黄金集分层：单域清晰（每域 20）、单域模糊（每域 10）、跨域（40）、**无法判断（30）**、对抗性（20）。

**"无法判断"这一类最关键**——测 clarify 出口会不会被硬猜。**不会说"我需要更多信息"的路由器，比不准的更危险。**

### 16. 什么时候不该做多 Agent

工具 <15、单轮无跨域、P95 <2s、团队 1–2 人、**没有单 Agent 基线**、拆完提升 <5% —— 任何一条命中，就别拆。
